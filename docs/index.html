edge-iot-sat-lab

A device with a bounded, prioritised, disk-backed queue publishing over MQTT through a link that drops out, to a ground station. The broker (mochi-mqtt) and client (Eclipse Paho) are real; the link is a TCP proxy that adds latency and cuts connections. All numbers are recorded from one real-time run of cmd/scenario. Personal learning project, not a satellite system.

How it behaves

Nothing is lost. A message leaves the queue only after the broker's acknowledgement, so a cut link means a retry, not a loss.

Duplicates are possible. With QoS 1, a message can be delivered twice if the link drops after the broker took it but before the device saw the acknowledgement. The ground station deduplicates by message id.

SOS goes first. When the link returns, the queue drains by priority, then arrival order. The SOS message was queued mid-outage and was delivered ahead of everything queued before it.

Corrupt sentences are rejected. Some telemetry carries a flipped character; the NMEA checksum catches it on the ground.

Not covered

No real radio, satellite or modem. The link model is latency plus hard outages, with no bandwidth cap, loss bursts or Doppler. No Bluetooth, Wi-Fi or LTE/5G handling in this repo; for cellular I have separate repos (nr-ca-analyzer, 6g-ran-edge-lab). No MQTT 5, no TLS, no broker clustering, and no tests of a full disk. The device and ground station run in one process on loopback.
